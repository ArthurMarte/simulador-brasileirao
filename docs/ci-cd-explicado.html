1. Para que serve este documento

Ver um pipeline funcionar e saber escrever um são coisas diferentes. Este documento existe para fechar essa distância.

Você já tem um arquivo ci.yml funcionando no seu repositório. Ele roda, fica verde, bloqueia merge quando algo quebra. Mas se amanhã alguém pedir para você configurar CI num projeto novo, do zero, provavelmente você travaria — porque entender um arquivo pronto é reconhecimento, e escrever um do zero é produção. São habilidades distintas.

Então o documento faz duas coisas. Primeiro, explica cada pedaço do arquivo que você já tem, sem pular nada por parecer óbvio. Depois, na seção 7, reconstrói um pipeline equivalente do zero, em cinco etapas, cada uma adicionando uma capacidade. Se você acompanhar essa segunda parte digitando junto num repositório de testes, sai sabendo fazer.

Pressuposto: você sabe usar o terminal e o git no básico, e não sabe nada de CI. Nenhum conhecimento prévio de YAML, Docker ou GitHub Actions é assumido.

2. O que é CI/CD

2.1 O problema que existia antes

Imagine uma equipe de cinco pessoas mexendo no mesmo projeto. Cada uma trabalha na sua máquina, com sua versão do Python, suas bibliotecas instaladas ao longo de meses, seu banco local com dados de teste antigos. Na sexta-feira, todo mundo junta o código.

O que acontece é previsível: o código de A depende de uma biblioteca que só existe na máquina de A. O teste de B passa porque o banco dele tem um registro que ninguém mais tem. O de C nem foi executado, porque rodar a suíte inteira demora oito minutos e ele estava com pressa. A frase que define esse mundo é "na minha máquina funciona".

O problema não é preguiça — é que a verificação depende de disciplina humana, e disciplina humana falha sob pressão. A solução foi tirar a verificação das pessoas e dar para uma máquina que não tem pressa, não tem sexta-feira e não tem máquina configurada de qualquer jeito.

Integração Contínua (CI) é isso: a cada envio de código, um servidor limpo baixa o projeto do zero, instala tudo do zero, e roda as verificações. Se qualquer uma falhar, ele avisa em minutos.

Entrega Contínua (CD) é o passo seguinte: se todas as verificações passaram, o mesmo servidor publica o código em produção automaticamente. Sem ninguém copiando arquivo, sem ninguém lembrando de rodar a migration.

2.2 A analogia do porteiro

A imagem que vale guardar

Pense num porteiro de prédio. Todo código que quer entrar no projeto passa por ele, sem exceção. O porteiro confere uma lista: o código está formatado no padrão? Os testes passam? A cobertura está acima de 80%? Se qualquer resposta for "não", o código fica na porta. Se tudo passa, o próprio porteiro leva o pacote até o servidor de produção.

Essa analogia carrega três ideias importantes. O porteiro é inflexível — ele não abre exceção porque você está com pressa; é justamente por isso que ele funciona. Ele confere em ordem, e para no primeiro problema, porque não faz sentido rodar dez minutos de teste num código que sequer está formatado. E ele é o mesmo para todo mundo: não existe "na máquina do porteiro funciona".

2.3 Onde isso mora

Na prática, o porteiro é um arquivo de texto dentro do seu próprio repositório, na pasta .github/workflows/. O GitHub lê esse arquivo automaticamente e executa o que estiver escrito nele.

Repare no que isso significa: não existe painel de configuração. Não existe servidor para instalar. A configuração do seu processo de qualidade é código versionado, que passa por revisão em pull request como qualquer outro arquivo, e cujo histórico de mudanças você consegue auditar com git log. Se alguém afrouxar uma regra, fica registrado quem foi e quando.

3. YAML em cinco minutos

O arquivo é escrito em YAML — um formato de configuração feito para ser lido por humanos. Ele tem pouquíssimas regras, e você precisa de todas elas.

3.1 Chave e valor

A unidade básica é chave: valor. O espaço depois dos dois-pontos é obrigatório.

name: CI/CD
runs-on: ubuntu-latest

3.2 Listas

Itens de uma lista começam com hífen e espaço. Há também a forma compacta, entre colchetes — as duas são idênticas para o computador.

# forma expandida
branches:
  - main
  - develop

# forma compacta — mesma coisa
branches: [main, develop]

3.3 Aninhamento pela indentação

Aqui está o ponto que confunde todo iniciante: em YAML, o recuo define a estrutura. Não há chaves nem parênteses delimitando blocos, como em JSON ou Python. O que está mais recuado pertence ao que está acima e menos recuado.

jobs:                      # chave de primeiro nível
  lint:                    # 2 espaços → é filho de "jobs"
    runs-on: ubuntu-latest # 4 espaços → é filho de "lint"
    steps:                 # 4 espaços → também filho de "lint"
      - run: echo "oi"     # 6 espaços → item da lista "steps"

Leia esse bloco como uma árvore: existe um jobs; dentro dele um job chamado lint; dentro do lint, duas configurações. A hierarquia inteira é comunicada por espaço em branco.

3.4 Textos de várias linhas

Dois operadores aparecem no seu arquivo. O | (barra vertical) preserva as quebras de linha — use para escrever vários comandos de shell:

- name: Smoke test
  run: |
    sleep 20
    curl -sf https://meu-app.fly.dev/api/health/

O >- faz o contrário: junta tudo numa linha só. Serve para quebrar um texto longo por legibilidade sem realmente quebrá-lo:

options: >-
  --health-cmd pg_isready
  --health-interval 5s

O que o Docker recebe ali é --health-cmd pg_isready --health-interval 5s, numa linha. As quebras existiam só para o seu olho.

3.5 Os três erros que todo mundo comete

ErroPor quê
Usar TAB para indentar YAML proíbe tabulação. Só espaço. O erro é found character '\t' that cannot start any token. Configure seu editor para converter TAB em espaços.
Recuo inconsistente Misturar 2 e 4 espaços no mesmo nível quebra a estrutura. Escolha 2 e mantenha.
Esquecer aspas em valores especiais python-version: 3.10 vira o número 3.1 — o zero final é descartado. Escreva "3.10". Vale também para on e off, que viram true e false.
Dica prática

Instale a extensão YAML (da Red Hat) no VS Code. Ela conhece o esquema do GitHub Actions e sublinha erro de indentação e nome de campo inválido enquanto você digita — antes de commitar e esperar dois minutos para descobrir.

4. O vocabulário do GitHub Actions

Sete palavras. Se você entender essas, o arquivo inteiro deixa de ser opaco.

TermoO que é
WorkflowO arquivo inteiro. Um processo automatizado completo. Você pode ter vários no mesmo repositório — um para CI, outro para publicar documentação, outro que roda de madrugada.
Trigger
on:		O que dispara o workflow: um push, a abertura de um pull request, um horário fixo, ou um clique manual.
JobUm bloco de trabalho. Cada job roda numa máquina virtual separada e limpa. Por padrão, jobs rodam em paralelo — a menos que você declare dependência.
StepUm passo dentro de um job. Steps rodam em sequência, na mesma máquina, e compartilham o disco.
RunnerA máquina virtual que executa. ubuntu-latest é a padrão, e é gratuita e ilimitada em repositório público.
Action
uses:		Um passo pronto, escrito por outra pessoa e reutilizado por você. actions/checkout@v4 baixa o seu código para dentro do runner.
SecretSenha ou token guardado criptografado nas configurações do repositório. Nunca aparece no código nem nos logs.
Service containerUm banco de dados ou Redis temporário que sobe só durante aquele job e morre no fim.
GateUma condição que, ao falhar, derruba o pipeline inteiro. Ex.: cobertura abaixo de 80%.

A diferença entre uses: e run:

Todo step é uma coisa ou outra, nunca as duas.

- uses: actions/checkout@v4   # executa uma ação pronta de terceiros
- run: pytest                 # executa um comando no shell do runner

Quando uma action precisa de parâmetros, eles vêm num bloco with::

- uses: actions/setup-python@v5
  with:
    python-version: "3.12"

O @v4 no fim do nome é a versão. Fixá-la importa: sem isso, uma atualização feita por terceiros poderia mudar o comportamento do seu pipeline sem você ter tocado em nada.

Máquina limpa, sempre

Um detalhe que explica metade dos erros de CI

Cada job começa numa máquina zerada: sem o seu código, sem suas bibliotecas, sem o seu .env. É por isso que todo job começa com actions/checkout — sem ele, o runner nem sabe o que é o seu projeto. E é por isso que qualquer coisa que só existe no seu computador simplesmente não existe lá.

Essa aspereza é a razão de o CI ser confiável. Se passa numa máquina zerada, passa em qualquer lugar.

5. A regra invisível: código de saída

Existe um mecanismo que o arquivo nunca menciona e do qual tudo depende.

Todo programa de terminal, ao encerrar, devolve um número ao sistema operacional. Por convenção universal: zero significa sucesso, e qualquer outro número significa falha. Isso é anterior ao GitHub, ao Git e à internet — vem do Unix.

O GitHub Actions apenas obedece a essa convenção. A regra completa é:

A regra

Se um comando run: termina com código diferente de zero, o step falha. Se um step falha, o job falha. Se um job falha, os jobs que dependem dele nem chegam a rodar, e o pipeline fica vermelho.

Isso explica por que o seu arquivo não tem nenhuma configuração dizendo "falhe se os testes falharem". O pytest já sai com código 1 quando algum teste quebra. O ruff já sai com código 1 quando encontra problema de formatação. O GitHub só está lendo esse número.

A consequência prática é libertadora: qualquer verificação que você consiga rodar no terminal, você consegue colocar no CI. Não precisa existir uma "action" para isso. Se o comando retorna zero quando está tudo bem, ele já serve como porteiro.

6. Anatomia do nosso ci.yml

Agora, o arquivo real, bloco por bloco.

6.1 Cabeçalho e gatilhos

name: CI/CD

on:
  push:
    branches: [main, develop]
  pull_request:
    branches: [main, develop]

O name é só o rótulo que aparece na aba Actions do GitHub. Não tem efeito nenhum na execução.

O on define quando o workflow roda, e aqui há duas situações distintas:

  • push — quando você envia commits para main ou develop. É o que acontece depois que um pull request é aprovado e mesclado.
  • pull_request — quando você abre ou atualiza um PR apontando para essas branches. Note a diferença: aqui o filtro é o destino do PR, não a branch de origem. Um PR vindo de feat/qualquer-coisa para a main dispara o workflow.

É essa segunda regra que faz a proteção de branch funcionar. O código é verificado antes de entrar na main, não depois.

Outros gatilhos úteis 
on:
  schedule:
    - cron: "0 3 * * *"   # todo dia às 3h UTC
  workflow_dispatch:      # adiciona um botão "Run workflow" na interface

6.2 Job 1 — Lint

jobs:
  lint:
    name: Lint
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-python@v5
        with:
          python-version: "3.12"
      - run: pip install ruff==0.8.4
      - run: ruff check .

Lendo de cima para baixo: lint é o identificador interno do job (usado por outros jobs para referenciá-lo); name é o rótulo bonito na interface; runs-on pede uma máquina Linux ao GitHub.

Os quatro steps, em ordem: baixa o código, instala o Python 3.12, instala o ruff numa versão fixa, e roda a verificação. O ruff check . examina todos os arquivos .py a partir do diretório atual. Achou problema de formatação ou import não usado, sai com código 1, e o job fica vermelho.

Duas decisões de projeto valem ser notadas aqui. A primeira é a versão fixa (ruff==0.8.4): uma versão nova do ruff pode introduzir regras novas, e sem o pin o seu pipeline quebraria sozinho num dia em que você não mexeu em nada. A segunda é que este job vem primeiro, porque leva segundos e é a verificação mais barata que existe. Falhar cedo e barato é um princípio de projeto de pipeline.

6.3 Job 2 — Testes e cobertura

Este é o job mais denso do arquivo. Vamos em quatro partes.

A dependência

  test:
    name: Testes + Cobertura
    runs-on: ubuntu-latest
    needs: lint

O needs: lint é o que transforma jobs paralelos em uma corrente. Sem essa linha, lint e test rodariam ao mesmo tempo. Com ela, test só começa se lint tiver terminado com sucesso — e se o lint falhar, o test é marcado como skipped e nem consome máquina.

Os service containers

    services:
      db:
        image: postgres:16-alpine
        env:
          POSTGRES_DB: test_db
          POSTGRES_USER: postgres
          POSTGRES_PASSWORD: postgres
        ports: ["5432:5432"]
        options: >-
          --health-cmd pg_isready
          --health-interval 5s
          --health-timeout 5s
          --health-retries 5
      redis:
        image: redis:7-alpine
        ports: ["6379:6379"]

Aqui o GitHub sobe dois contêineres Docker ao lado do seu job: um PostgreSQL e um Redis. Eles nascem quando o job começa, ficam acessíveis em localhost, e são destruídos quando o job termina. É por isso que você não precisa de um banco "de verdade" hospedado em algum lugar só para rodar testes.

O bloco options merece atenção especial, porque é a origem de um erro clássico. Um contêiner Postgres leva alguns segundos entre "iniciado" e "pronto para aceitar conexões". Sem o healthcheck, o seu job começaria a rodar imediatamente e o pytest tentaria conectar num banco que ainda está subindo — resultando em connection refused, de forma intermitente e difícil de reproduzir.

O que as quatro linhas dizem: execute o comando pg_isready a cada 5 segundos, desistindo de cada tentativa após 5 segundos, até 5 tentativas. O job só começa quando esse comando responder que o banco está pronto.

Erro clássico

connection refused no banco, falhando às vezes sim e às vezes não, quase sempre significa healthcheck ausente ou mal configurado. É o exemplo perfeito de bug de concorrência: não é o seu código que está errado, é a ordem em que as coisas ficaram prontas.

As variáveis de ambiente

    env:
      SECRET_KEY: chave-de-teste
      DEBUG: "False"
      DATABASE_URL: postgres://postgres:postgres@localhost:5432/test_db
      REDIS_URL: redis://localhost:6379/0
      FOOTBALL_DATA_TOKEN: token-falso-para-testes

Lembre que a máquina é zerada e o .env não existe lá — ele está no .gitignore, e ainda bem. Este bloco recria as variáveis que a aplicação precisa para iniciar. Sem o SECRET_KEY, por exemplo, o Django nem carrega as configurações, e você veria um KeyError: 'SECRET_KEY'.

Repare que o host no DATABASE_URL é localhost, e não db como no seu docker-compose.yml. Os service containers do GitHub publicam suas portas direto na máquina do runner, então o seu código os enxerga como se estivessem na mesma máquina.

E repare no valor do token: token-falso-para-testes. Isso não é descuido — é requisito. Nenhum teste pode fazer chamada de rede real; as respostas da API externa são substituídas por dados capturados previamente. Se algum teste tentasse chamar a API de verdade, ele falharia com esse token, e é exatamente esse o objetivo: um teste que precisa de internet é um teste que vai falhar em algum momento por motivo alheio ao seu código.

Os steps e o gate de cobertura

    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-python@v5
        with:
          python-version: "3.12"
          cache: pip
      - run: pip install -r requirements-dev.txt
      - name: Rodar testes (gate de 80% de cobertura)
        run: pytest
      - uses: actions/upload-artifact@v4
        if: always()
        with:
          name: coverage
          path: coverage.xml

O cache: pip guarda as bibliotecas baixadas entre execuções. Sem isso, cada rodada baixaria Django, DRF e todo o resto da internet de novo. Costuma reduzir o tempo do job pela metade.

O if: always() no último step é sutil e útil: por padrão, quando um step falha, os seguintes são pulados. Esse always() diz "guarde o relatório de cobertura mesmo se os testes falharam" — porque é justamente quando falha que você quer olhar o relatório.

Onde fica o gate de 80%

Não está neste arquivo. Está no pytest.ini, na linha --cov-fail-under=80. O pytest sai com código de erro se a cobertura ficar abaixo disso, e o CI apenas reflete essa falha.

A vantagem dessa escolha é grande: a regra é a mesma na sua máquina e no servidor. Você descobre que quebrou o gate rodando pytest localmente, em vez de descobrir dois minutos depois de um push.

6.4 Job 3 — Deploy

  deploy:
    name: Deploy
    runs-on: ubuntu-latest
    needs: test
    if: github.ref == 'refs/heads/main' && github.event_name == 'push'
    steps:
      - uses: actions/checkout@v4
      - run: echo "Configure a plataforma de deploy aqui"

O needs: test fecha a corrente: lint → test → deploy. Nada é publicado sem ter passado pelas duas verificações anteriores.

A linha if: é a mais importante e merece ser lida com calma. Ela impõe duas condições simultâneas:

  • github.ref == 'refs/heads/main' — estamos na branch main. Código em branch de feature nunca vai para produção.
  • github.event_name == 'push' — o evento é um push, não um pull request. Sem isso, abrir um PR publicaria código ainda em revisão.

É por isso que, na tela de um pull request, o job Deploy aparece como Skipped. Não é erro — é a condição funcionando como projetada.

O ${{ ... }} que aparece em outros trechos é a sintaxe de expressão do Actions. Dentro dele você acessa contextos como github (dados do evento) e secrets (os valores criptografados).

Como fica quando o deploy estiver ativo

    steps:
      - uses: actions/checkout@v4
      - uses: superfly/flyctl-actions/setup-flyctl@master
      - run: flyctl deploy --remote-only
        env:
          FLY_API_TOKEN: ${{ secrets.FLY_API_TOKEN }}
      - run: flyctl ssh console -C "python manage.py migrate --noinput"
      - name: Smoke test
        run: |
          sleep 20
          curl -sf https://SEU-APP.fly.dev/api/health/ || exit 1

Três coisas acontecem aqui, nesta ordem obrigatória: publica o código, aplica as migrations no banco de produção, e verifica que a aplicação respondeu.

O smoke test é o passo que quase todo mundo esquece, e é o que separa um pipeline decorativo de um pipeline confiável. Sem ele, um deploy pode terminar "com sucesso" enquanto a aplicação está quebrada em produção — e você só descobre quando um usuário reclama. O curl -sf devolve código diferente de zero se a resposta não for bem-sucedida, e aquela regra invisível da seção 5 faz o resto: pipeline vermelho em trinta segundos.

Sobre o FLY_API_TOKEN: o valor vem de Settings → Secrets and variables → Actions. Secrets são criptografados, não podem ser lidos de volta pela interface, e são automaticamente mascarados nos logs — se um comando imprimir o token por acidente, o GitHub substitui por ***.

7. Construindo um pipeline do zero

Esta é a seção que responde ao "se eu tiver que fazer, eu não sei". Cinco etapas, cada uma adicionando uma capacidade. Faça num repositório de testes separado.

Etapa 1 — O "olá mundo"

Crie o arquivo .github/workflows/ci.yml. A pasta precisa ter exatamente esse nome; é onde o GitHub procura.

name: Meu primeiro pipeline

on: [push]

jobs:
  ola:
    runs-on: ubuntu-latest
    steps:
      - run: echo "O pipeline rodou!"

Commite, envie, e abra a aba Actions. O objetivo aqui não é fazer algo útil — é ver o ciclo completo funcionando e entender que o arquivo é lido automaticamente. Não avance enquanto isso não estiver claro.

Etapa 2 — Trazer o código e a linguagem

jobs:
  lint:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-python@v5
        with:
          python-version: "3.12"
      - run: pip install ruff
      - run: ruff check .

Agora o pipeline faz algo real. Experimente deliberadamente: deixe um import não usado num arquivo .py, commite, e veja o job ficar vermelho. Depois corrija e veja ficar verde. Provocar a falha de propósito é o exercício mais valioso desta seção — é o que ensina a confiar no porteiro.

Etapa 3 — Rodar os testes com banco

  test:
    runs-on: ubuntu-latest
    needs: lint
    services:
      db:
        image: postgres:16-alpine
        env:
          POSTGRES_PASSWORD: postgres
        ports: ["5432:5432"]
        options: >-
          --health-cmd pg_isready
          --health-interval 5s
          --health-retries 5
    env:
      DATABASE_URL: postgres://postgres:postgres@localhost:5432/postgres
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-python@v5
        with:
          python-version: "3.12"
          cache: pip
      - run: pip install -r requirements-dev.txt
      - run: pytest

Três conceitos novos entram de uma vez: needs (a corrente), services (o banco temporário) e env (as variáveis que a máquina zerada não tem). Se algo falhar aqui, quase sempre é uma variável de ambiente faltando — leia a mensagem de erro procurando por um nome de variável.

Etapa 4 — O gate de cobertura

Não se escreve no YAML. No pytest.ini:

[pytest]
addopts =
    --cov=apps
    --cov-report=term-missing
    --cov-fail-under=80

O pytest do step anterior já passa a respeitar isso, sem nenhuma mudança no workflow. Vale internalizar o princípio geral: a regra mora na ferramenta, o CI só executa a ferramenta. Isso mantém local e servidor idênticos, e evita que seu YAML vire um depósito de configuração.

Etapa 5 — O deploy condicional

  deploy:
    runs-on: ubuntu-latest
    needs: test
    if: github.ref == 'refs/heads/main' && github.event_name == 'push'
    steps:
      - uses: actions/checkout@v4
      - run: echo "publicar aqui"
        env:
          TOKEN: ${{ secrets.MEU_TOKEN }}

Comece com o echo como placeholder, exatamente como está no seu projeto. Confirme que a condição funciona — que ele roda em push na main e é pulado em PR — antes de colocar o comando de publicação de verdade. Depurar a condição e o deploy ao mesmo tempo é pedir para sofrer.

A regra de ouro

Faça na mão uma vez antes de automatizar. Publique manualmente pelo terminal, entenda cada comando, veja a aplicação no ar. Só então transcreva para o YAML. Automatizar um processo que você nunca executou é a receita para não saber depurar quando quebrar.

8. Quando fica vermelho

Vai ficar. Faz parte do processo, e não é sinal de que você errou — é o porteiro fazendo o trabalho dele. O que importa é saber ler.

Como investigar

  1. Abra a aba Actions e clique no job vermelho. Cada step vira uma linha expansível com o log completo. O step que falhou tem um X.
  2. Leia de baixo para cima. A mensagem final costuma ser a causa; o resto é ruído acumulado. Essa é a técnica mais subestimada de depuração.
  3. Reproduza localmente antes de tentar consertar. Rode o mesmo comando na sua máquina. Se passa local e falha no CI, a diferença está no ambiente: variável faltando, versão diferente, banco não pronto.
O antipadrão

Commitar às cegas para "ver se passa agora" desperdiça tempo, polui o histórico com mensagens como "tenta de novo", e não ensina nada. Se você não sabe por que falhou, ainda não é hora de commitar.

KeyError: 'SECRET_KEY'Variável faltando no bloco env: do job.
connection refused no bancoFalta o healthcheck; os testes começaram antes do Postgres ficar pronto.
relation ... does not existMigration não commitada. Rode makemigrations e versione o arquivo gerado.
Cobertura abaixo de 80%Código novo sem teste. Rode pytest --cov-report=term-missing e veja as linhas descobertas.
Passa local, falha no CITeste dependente de ordem, de cache sujo ou de arquivo que só existe na sua máquina.
O deploy não rodaA condição if: não foi satisfeita — provavelmente você não está na main, ou o evento é pull_request.
Bad credentialsSecret com nome errado ou token expirado.
found character '\t'TAB no YAML. Troque por espaços.

9. Referência rápida

Esqueleto mínimo

name: <nome que aparece na aba Actions>

on:
  push:
    branches: [main]
  pull_request:
    branches: [main]

jobs:
  <id-do-job>:
    name: <rótulo na interface>
    runs-on: ubuntu-latest
    needs: <job anterior>          # opcional: cria dependência
    if: <condição>                 # opcional: executa só se verdadeiro
    services: { ... }              # opcional: bancos temporários
    env: { ... }                   # opcional: variáveis do job
    steps:
      - uses: <action>@<versão>
        with: { ... }
      - name: <descrição>
        run: <comando de shell>

Actions de uso frequente

ActionPara quê
actions/checkout@v4Baixa o repositório para o runner. Praticamente todo job precisa.
actions/setup-python@v5Instala uma versão do Python. Use cache: pip.
actions/upload-artifact@v4Guarda arquivos gerados (relatórios, builds) para download.
actions/cache@v4Cache genérico, quando o setup-python não basta.
